三、统一的简化原则

3.1 Notebook 自包含

四份 notebook 都不得导入下列项目内实现：

- from configs import ...
- from ZZworkbench.project_progress_reliable import ...
- from ZZworkbench.rag_langchain.text_retrieval import ...
- 另一个 ipynb 中定义的变量或函数

允许直接读取：

- knowledge/project_progress/texts/v4/*.txt
- knowledge/project_progress/evals/retrieval_v4.jsonl
- knowledge/project_progress/evals/reliability_v4.jsonl

允许导入：

- Python 标准库；
- langchain_core；
- langchain_text_splitters；
- langchain_huggingface；
- rank_bm25；
- langgraph；
- 当前 notebook 实际使用的其他已安装 LangChain 官方包。

3.2 简单路径配置

只支持两种实际启动位置：

- 仓库根目录；
- ZZworkbench 目录。

用几行直接判断当前目录即可，不建立通用仓库发现框架，不修改 sys.path，不导入私有 configs.py。

所有展示给用户的 source 优先使用相对路径或 source_name；输出中不要打印用户主目录绝对路径。

3.3 控制抽象数量

- 函数只有在被复用、需要单独测试，或其名字能明确表达一个业务阶段时才定义；
- 一次使用且少于约 10 行的展示逻辑直接写在代码单元中；
- 不为返回三组 list 创建 dataclass；
- 不为一份 BM25 index 创建只有一个 search 方法的业务 class；
- 普通 dict 足以表达 QueryIntent、record、trace 和 result 时，不创建数据 class；
- 不出现“函数 A 只调用函数 B，函数 B 只包装函数 C”的调用链；
- 不使用隐藏全局可变状态；
- 允许 notebook 之间有少量重复代码，自包含和可读性优先于为了 DRY 再抽共享模块。

3.4 控制工程范围

本轮不做：

- 新增共享 Python 模块；
- 大范围修改现有 text_retrieval.py 或 project_progress_reliable.py；
- 持久化 Chroma/Qdrant/FAISS 索引；
- 索引 manifest、缓存失效协议或生产部署设计；
- LangSmith tracing；
- LLM query rewrite、Self-Query、Multi-Query、Agent 或 Deep Agents；
- 无限 fallback、自动反思、长期 memory；
- 为了演示而生成新语料或新业务假设。

3.5 正确解释检索分数

- 当前 InMemoryVectorStore 使用 cosine similarity，with_score 分数越大越相关；
- search_type 不负责选择 Cosine / Inner Product / L2，具体度量由 VectorStore 实现决定；
- Retriever.invoke 通常只返回 Document，with_score 是 VectorStore 级调试接口；
- BM25 score 与 cosine score 不在同一尺度，不直接线性相加；
- RRF 使用排名融合；
- 当前安装版 InMemoryVectorStore 没有实现 relevance-score 映射，
  similarity_score_threshold retriever 调用会抛 NotImplementedError；
- 本轮如演示阈值，使用 similarity_search_with_score 后按原始 cosine 手动过滤，并明确这是当前实现相关行为；
- 阈值必须由当前模型、当前语料和标注样例校准，不能写成通用常数。

必须保留的业务流程：

查询规范化
→ 工程 metadata route
→ 中文 BM25
→ Dense 补充
→ Weighted RRF
→ 完整任务记录定位
→ Evidence Gate
→ 引用回答或拒答

必须内联到 notebook 的最小代码：

2. 生成稳定 document_id/chunk_id；

6. 中文 mixed tokenizer；
7. BM25 搜索；
8. Dense with_score 搜索；
9. weighted_rrf；
10. 单个 query_schedule 或 answer_query 编排函数；
11. Evidence Gate；
12. JSONL 评测读取与简短评测循环。

数据结构要求：

- QueryIntent 使用普通 dict；
- task record 使用普通 dict；
- retrieval trace 使用普通 dict；
- result 使用普通 dict；

  ReliableQueryResult 等 class/dataclass；
- BM25 模型、chunks、records 可以是 notebook 顺序执行后产生的只读变量；
- 每个阶段最多一层清晰函数，不再套 adapter/wrapper。

Evidence Gate 至少覆盖：

- 没有识别到任务；
- 工程范围内没有记录；
- 同名任务跨工程歧义；

- exact 才输出模板化事实与引用；
- 其他情况返回 ambiguous、not_found 或 insufficient。

领域优化必须有实际依据：

- 工程别名只写当前文档真实存在的别名；
- 不构造不存在的组织、权限、用户、数据库等 metadata；
- 不把 embedding 相似度当正确概率；
- 不为了“高级”加入 LLM rewrite；
- 若完整任务记录已经能映射到现有 chunk，不重做复杂 parent-child/multi-vector 索引。

验证：

- 运行 retrieval_v4.jsonl；
- 运行 reliability_v4.jsonl；
- 报告通过数和失败明细；
- 当前样例若 13/13 通过，只能称为本知识库防回归结果，不能称为通用 RAG 准确率；
- 保留“错误 chunk 导致 Evidence Gate 拒答”的最小反例，但用 1 个短单元完成。

定位：LangChain Retriever 接口与组件边界教学，不再承担完整生产 RAG 设计。

2. 为什么 Retriever 是 Runnable，而 VectorStore 不是？
3. as_retriever 的 similarity 与 mmr 如何配置？
4. 为什么 with_score 通常在 VectorStore 层调用？
5. 如何把一个已经验证的 retriever 暴露成 tool？

要求：

- 开头只保留一个简短流程图或一张表，不保留多个大型 ASCII 图；

- with_score 直接调用 VectorStore；

4.4 static_retrieve_langgraph.ipynb

定位：用最小 graph 解释 LangGraph 的编排价值，不把简单查询包装成复杂状态机。

保留的概念：

- State；
- Node；
- Edge；
- Conditional Edge；
- compile/invoke；
- 框架只编排，不改善 retriever。

核心 graph 最多保留四个节点：

START
→ retrieve
→ evidence_gate
→ answer 或 refuse
→ END

实现要求：

- 查询规范化和 metadata filter 可以直接放在 retrieve node 中；
- state 使用一个小型 TypedDict；
- state 只保留 question、normalized_query、hits、status、answer、
  citations 等确实会跨节点使用的字段；
- hits 直接保存简化后的普通 dict，不实现 serialize_hit + deserialize_hit 双向适配；
- evidence_gate 只做一次明确判断；
- answer/refuse 使用条件边展示分支；
- 不实现 fallback_retrieve；
- 不实现多个 exact/ambiguous/not_found/conflict 专用终止节点；
- 不实现无限循环、query rewrite、Agent；
- 默认不使用 checkpointer；
- 若保留 InMemorySaver，只放在核心 graph 之后的独立小节，用一个 thread_id
  演示状态快照，不把 checkpoint 变成主流程依赖；
- 用 success、ambiguous/not_found 两到三个真实问题展示路径；
- 将 graph 输出与同一 notebook 中的直接函数输出对比，事实和引用应一致；
- 明确结论：当前单跳查询默认仍应调用直接 pipeline，LangGraph 仅在确有分支、
  恢复、人工审核或多步骤状态需求时才值得引入。

与 level1a 的关系：

- 可以在本 notebook 内放置一个缩短版、可读的检索函数；
- 不导入 level1a，也不导入项目共享模块；
- 不必复制 level1a 的全部 13 条评测和所有领域规则；
- 只复制 graph 示例真正需要的最小数据加载、检索和证据判断。

- 组件示例短而可运行；
- 高级组件只解释，不为展示而堆实现。

static_retrieve_langgraph 验收：

- 核心 graph 不超过四个节点；
- 至少有一条 conditional edge；
- 无 fallback 循环；
- 无隐藏项目模块；
- graph 与直接函数对相同问题给出一致事实/引用或一致拒答；
- 明确说明 graph 的收益是流程编排与可观察性，不是检索准确率自动提升。

九、自审结论

本需求稿已做以下取舍：

1. “全部代码在 notebook”与 DRY 有冲突。本任务选择 notebook 独立可读，允许少量重复，
   但禁止再抽共享模块制造跳转。
2. level1 保持朴素，因此不承担工程日期事实正确性；只输出候选和来源。
3. level1a 保留领域 route、完整任务记录和 Evidence Gate。这些不是过度设计，
   而是当前知识库中处理同名任务和日期归属的必要约束。
4. static_retrieve_langchain 只讲框架接口，不再同时建设持久化索引系统。
5. static_retrieve_langgraph 保留一个条件分支来体现框架设计，但删除 fallback、
   多终止节点和大规模状态适配。
6. 当前 13 条样例只作为本知识库防回归，不据此声称方案具有通用可靠性。
7. 本轮不包含 Deep Agents；若后续继续，应在直接 pipeline 和最小 graph 稳定后单独处理。

审核重点：

- 是否同意 level1 只做到“候选检索”，不承担领域 Evidence Gate；
- 是否同意 level1a 保留领域可靠性，但改用普通 dict + 少量函数；
- 是否同意 static_retrieve_langchain 取消持久化 Chroma 主流程；
- 是否同意 static_retrieve_langgraph 核心限制为四个节点且取消 fallback。
