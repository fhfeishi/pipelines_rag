一、已确认的工程事实

当前 v4 知识库实际情况：

- 8 份 TXT 文档；
- 合计约 103 KB、1120 行；
- 每份文档对应一个工程或一个工程分册；
- 文本已被整理成半结构化任务记录，常见字段为工程名、任务标识号、父子任务、任务名、工期、计划开始、计划完成、PDF 页码；
- 当前评测集只有 8 个单跳事实问题，主要查询某工程中某任务的开始日期、完成日期或工期；
- 不同工程中存在大量相同或相近任务名。例如“施工准备”至少出现在江湾、黄金、三虎土建、禾益等多个文档中；
- 工程名存在“110kV/110千伏”、是否带“珠海”、简称与全称等表达差异；
- 部分文档包含父子任务层级，也可能存在异常工期文本，因此不能只凭相似度最高的 chunk 直接回答。

由此得到的工程判断：

1. 这个场景不是开放域语义搜索，而是“小型、半结构化、强实体约束”的事实查询。
2. 语义向量检索可以补充口语改写召回，但不能单独承担工程隔离、同名任务消歧和日期正确性保证。
3. 可靠性首先来自工程范围识别、任务词面匹配、同一任务记录字段完整性、冲突检测、引用和拒答。
4. LangGraph 与 Deep Agents 只能编排这些可靠组件，不能把不可靠的 retriever 自动变可靠。
5. 对当前 8 个单跳问题，直接的确定性 pipeline 应继续作为首选基线；只有复合查询才可能需要 Agent。

每份 notebook 都要清楚回答：

1. 这个框架的设计理念是什么，处在 LangChain 技术栈的哪一层？

四、共同的可靠 RAG pipeline

两份 notebook 必须建立在同一个可靠检索/证据契约上。先比较，再决定是否引入框架。

4.1 三条对照路径

至少比较：

A. dense-only：现有向量检索基线；
B. hybrid：现有工程 metadata route + 中文 n-gram BM25 + dense + weighted RRF；
C. reliable pipeline：查询规范化 + 工程消歧 + hybrid 候选召回 + 任务记录定位 + 字段完整性校验 + 引用/拒答。

不能预设 C 一定更好，必须用实际问题和失败样例验证。

4.2 查询契约

将每个问题转换为可检查的 QueryIntent，至少包含：

- original_query：原问题；
- normalized_query：统一全半角、空白、110kV/110千伏等写法后的问题；
- project_hint：工程名或工程简称；
- task_hint：任务名称；
- requested_fields：start_date、end_date、duration 等；
- query_type：single_lookup、multi_lookup、ambiguous 或 unsupported；
- diagnostics：规范化和解析说明。

首版优先使用可解释的规则、标题元数据和知识库内实际别名。不要为了展示 AI 而使用 LLM 抽取一个规则已经能稳定得到的工程名和日期字段。

4.3 候选召回

按以下优先级处理：

1. 若问题明确包含工程名，先限定到对应文档或分册；
2. 在工程范围内优先使用任务名词面匹配/BM25；
3. dense retrieval 用于口语改写和近义表达的补充召回；
4. 使用现有 weighted RRF 融合，不直接相加不可比的 BM25 与向量原始分数；
5. 没有明确工程时，只有任务在全库唯一且证据充分才可直接回答；同名任务跨工程出现时必须澄清或拒答。

不要把 embedding 相似度解释成事实正确概率，也不要仅凭一个固定阈值宣称答案可靠。

4.4 任务记录定位

召回 chunk 后，需要在 chunk 或相邻上下文中定位完整任务记录。证据单元应尽量包含：

- source/source_name；
- document_id、chunk_id；
- project_title；
- page；
- task_id、task_name；
- parent_task/task_path（文档存在时）；
- duration、start_date、end_date；
- 原始证据文本；
- dense/BM25/fused 排名信号。

是否新增 record-aware chunking 必须由实际审计决定：先检查当前 character chunk 是否切断任务记录；只有发现真实失败时才实现最小改动，不能为了“高级”重做整个索引。

4.5 Evidence Gate

回答前执行确定性证据检查，输出 exact、ambiguous、not_found、insufficient 或 conflict：

- 工程范围是否与 project_hint 一致；
- task_name 是否与 task_hint 精确或经过已知别名匹配；
- 请求的日期/工期字段是否出现在同一条任务记录中；
- 父任务与子任务是否被正确区分；
- 多个候选是否给出冲突字段；
- 引用元数据是否完整。

只有 exact 才进入确定性回答。ambiguous 应指出需要补充哪个工程或任务层级；not_found/insufficient/conflict 必须明确拒答或提示冲突。

4.6 Answer Contract

单条事实查询优先使用模板化回答，不要求 LLM：

- 直接给出任务、开始、完成、工期中用户实际询问的字段；
- 附 source、task_id/chunk_id 等引用；
- 不把未请求字段和模型常识混入答案。

LLM 仅用于复合结果的语言组织。LLM 只能读取已通过 Evidence Gate 的结构化证据，不能自行再次检索或补日期。

五、static_retrieve_langgraph.ipynb

5.1 设计理念

结合当前场景解释：

- LangGraph 是低层 orchestration/runtime，不是 retriever；
- State 使每一步输入、输出和失败原因可观察；
- Node 表示边界清晰的处理步骤；
- Conditional Edge 把“回答、澄清、拒答、有限 fallback”变成显式控制流；
- Checkpointer 保存线程内 graph 状态，便于恢复和调试；
- durable execution、HITL、memory 是框架能力，但当前单次静态查询不需要全部启用。

说明为什么本项目选择显式 graph，而不是无限循环的 ReAct Agent。

5.2 实际 graph

建议状态流：

START
  -> normalize_query
  -> parse_intent
  -> resolve_project
  -> retrieve_candidates
  -> locate_task_record
  -> evidence_gate
       -> exact -> format_answer -> END
       -> ambiguous -> request_clarification -> END
       -> not_found/insufficient 且未 fallback -> fallback_retrieve
       -> not_found/insufficient 且已 fallback -> abstain -> END
       -> conflict -> report_conflict -> END

要求：

- 最多两次 retrieval，默认一次；
- fallback 只做已定义的别名扩展、放宽工程路由或 dense 补充召回，不能无限改写 query；
- 不默认调用 LLM；
- 每个 node 返回 state 更新，不依赖隐藏的全局可变状态；
- state 只保存可序列化数据，不放 Chroma client、embedding model 或文件句柄；
- graph 中的 Evidence Gate 与直接 pipeline 复用同一个函数，不能出现两套判定规则。

5.3 必须展示的真实案例

- 直接成功：从现有 8 条评测中选择一条；
- 工程别名：例如 110kV/110千伏的规范化；
- 真实歧义：“施工准备什么时候完成？”在多个工程中存在，不能任选一条回答；
- 不存在任务：从语料确认不存在后，验证 not_found；
- 父子任务：从有层级的文档选择真实案例，展示任务层级不会混淆。

5.4 Checkpoint 教学

使用 InMemorySaver 和 thread_id 演示 state/history。解释 checkpoint、短期会话状态和跨线程长期记忆的区别。当前知识库不需要把检索证据写入长期记忆，不引入 SQLite/Postgres。

5.5 评测

除原有 source_hit@k、term_hit@k 外，报告：

- project_route_accuracy；
- exact_record_match；
- requested_field_completeness；
- citation_accuracy；
- ambiguity_detection；
- abstention_accuracy；
- 平均 retrieval 次数和 fallback 比例。

与直接 reliable pipeline 比较。若准确率相同，应诚实说明 LangGraph 的收益是流程可观察、分支可测试和状态可恢复，而不是检索质量自动提升。

六、static_retrieve_deepagents.ipynb

6.1 设计理念

结合当前场景解释：

- Deep Agents 是建立在 LangChain/LangGraph 上的 opinionated agent harness；
- 它提供长期任务规划、工具使用、上下文管理、临时文件空间和 subagent 等默认能力；
- 它适合复杂、多步骤、路径不能完全预先写死的任务；
- 它依赖支持 tool calling 的 LLM，因此比直接 pipeline 更慢、更贵、可预测性更低；
- 对当前 8 个单跳事实问题，Deep Agents 通常不是合理默认方案。

介绍 filesystem、skills、memory、subagents 的理念即可；不要为了展示功能而给这个小知识库开启宿主文件系统、shell、长期记忆或多个 subagent。

6.2 可靠工具边界

Deep Agent 不能直接访问 Chroma、原始文件或自由拼接检索逻辑。只暴露一个经过验证的只读工具，例如：

lookup_project_schedule(
    project: str,
    task: str,
    fields: list[str]
) -> {
    status,
    records,
    citations,
    diagnostics
}

要求：

- 工具内部调用与 LangGraph 相同的 reliable pipeline；
- 输入字段有 schema，fields 只允许 start_date/end_date/duration；
- k、fallback 次数等由工具内部限制，不交给 Agent 任意放大；
- ambiguous/not_found/conflict 原样返回，Agent 不得改写为确定答案；
- 工具输出保留 source、task_id/chunk_id 和证据文本；
- 工具只读，不写索引、不访问 shell、不读取 .env 或无关文件。

6.3 单跳问题：负责任地证明“无需 Agent”

选择与基准相同的一条日期问题，比较：

- 直接 reliable pipeline；
- Deep Agent 调用工具后的结果；
- 引用是否一致；
- 检索次数、LLM/tool 调用次数、耗时和 token。

结论必须由运行结果支持。预期应明确指出：单跳事实查询优先使用直接 pipeline。

6.4 复合问题：Deep Agents 的合理用例

使用完全来自现有评测数据的复合任务，例如：

“汇总南溪地基基础施工的计划起止时间、黄金主体结构封顶的计划完成时间、三虎电气全站电缆敷设安装的计划起止时间，并分别给出来源；任何一项证据不足都单独标记。”

该任务需要多次受控 lookup、结果核对和统一表达，适合展示 planning 与 tool orchestration。

要求：

- 限制最大工具调用次数；
- 展示 Agent 计划、工具输入、结构化返回和最终引用；
- 每个事实分别通过 Evidence Gate；
- 不把 Agent 计划、摘要或模型记忆作为证据；
- 一项失败不能污染其余已验证结果。

6.5 为什么暂不使用 subagent/filesystem

用一节短说明做工程决策：

- 当前数据只有 8 文档，检索工具输出很小，不存在需要 subagent 隔离的大上下文；
- 当前任务不产生需要文件系统管理的大型中间产物；
- 多开 subagent 会增加调用成本和非确定性；
- 因此首版只展示 Deep Agents 的 planning + tool calling + StateBackend；
- 后续只有在多知识源、大结果集或长报告任务出现时，再用实际评测决定是否引入 subagent。

这不是缺少功能，而是尊重当前工程规模后的选择。

6.6 Agent 层评测

报告：

- tool_selection_accuracy；
- tool_argument_accuracy；
- verified_fact_coverage；
- citation_completeness；
- invalid_claim_count；
- abstention/ambiguity preservation；
- LLM 调用次数、工具调用次数、耗时和 token。

检索质量仍使用共同的 retrieval 指标，不能用“Agent 最终回答看起来不错”替代评测。

七、评测集补充要求

保留现有 8 条正例，不能回归。新增少量、全部可从 v4 语料核验的 reliability cases：

- 工程别名；
- 无工程名且任务名跨工程重复；
- 不存在任务；
- 父任务/子任务消歧；
- 同一记录的开始+完成+工期多字段查询；
- 上述三项真实任务组成的复合查询。

不要编造不存在的工程、日期或业务规则。每条新增 case 要写清 expected_status、expected_source 和适用时的 expected_fields。

十三、自审结论

本稿已按实际工程场景做以下收敛：

1. 从通用 Agent 功能展示改为 8 文档进度知识库的可靠事实查询；
2. 将语义检索降为补充召回，增加工程路由、任务记录与字段校验；
3. 将 LangGraph 的重点从 LLM rewrite 改为显式 Evidence Gate 和有界 fallback；
4. 将 Deep Agents 限定为复合查询编排，单跳查询保留直接 pipeline；
5. 删除首版强制 subagent、真实 filesystem、shell、长期记忆的要求；
6. 所有示例均来自当前 v4 文档或既有 eval，不假设不存在的数据源和业务流程；
7. “可靠”被定义为可测的路由、记录匹配、字段完整、引用、歧义和拒答，而不是模型主观自评。
